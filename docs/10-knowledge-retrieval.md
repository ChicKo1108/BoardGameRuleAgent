# 知识快照与关键词检索基线

## 当前可运行范围

实现审核资料 → 不可变知识清单 → 完整规则索引 → 中文关键词检索 → 来源定位与关联规则补全。接口仅供已认证管理员实验；还没有公众问答、向量召回、融合重排、发布门禁或线上版本指针。

这个基线对应评测矩阵中的关键词方案。后续要与向量、混合、重排方案在同一审核数据集上比较；目前合成用例证明工程约束和链路，不能证明《花砖物语》真实问题的召回率。

## 两层不可变产物

- `knowledge_releases`：审核知识快照，含 ruleset、资料修订、规则、来源与关系的完整 manifest 和 SHA-256。
- `index_builds`：某一快照在固定切分/分词配置下的检索产物；重建索引不改知识内容。

快照在事务内 `assembling → sealed`，索引在事务内 `building → ready`。中间态对接口不可见，异常整体回滚。这两个状态是内容构建状态，不表示已通过评测或已上线。后续发布/回滚通过独立发布记录与版本指针完成，不改写已经冻结的 manifest。

同一规则集、相同资料修订集合的请求复用已有快照，保留第一次的名称；同一快照、相同配置复用索引。并发请求也只产生一份对应产物与一条创建审计。现阶段索引是有限大小的同步管理操作；耗时向量生成将另行接入持久 Worker。

## 数据库约束

- 只允许同一 ruleset 内已批准的修订，每份文档最多选一个修订，不能混入基础版之外的资料。
- 快照自动包含所选修订的所有规则，不能遗漏不方便召回的条件或例外。审批前规则与来源完整性沿用知识仓储约束。
- manifest 由数据库按真实成员、已冻结原文与关系构造，稳定排序后以 PostgreSQL JSONB 文本序列化计算 SHA-256。客户端不能提供自造 manifest/hash。
- manifest 包括经审核正文、编辑解释、原文块、PDF 页索引/印刷页码/坐标、文档哈希和关系。编辑解释始终单独存放。
- 快照与其成员冻结后不可增删改；有快照的规则集也不得原地改范围或归属，应创建新的 ruleset。
- 索引必须覆盖每个成员规则，片段的 release/build/rule 归属由复合外键约束；完成后配置与片段不可修改。
- 当前上限：100 个修订、2000 个规则、8 MiB manifest。超过限制报错，不偷偷舍弃内容。迁移回退会删除这些表，只应在备份后或隔离测试库使用。

## 切分与中文分词

`complete-rule-v1` 使用一条审核规则对应一个片段，正文不截断。检索文本为章节、适用条件和审核正文；编辑解释不参与关键词索引。超过 8000 个 JavaScript 字符单位的完整检索文本返回 `RULE_REQUIRES_SEMANTIC_SPLIT`，需要在新资料修订中按语义重新整理规则，避免按固定长度切断条件。

当前分词基线为 `Intl.Segmenter('zh-CN', { granularity: 'word' })`：NFKC 归一化、大小写统一、提取文字/数字词元，再将分好的词元交给 PostgreSQL `simple` 词典构建 `tsvector`。不是直接让 PostgreSQL 默认解析器分中文。

索引记录 chunker/tokenizer 版本、ICU 版本和长度配置。查询使用同一实现；运行时 ICU 不匹配时拒绝检索，必须用匹配运行环境或构建新索引，不能悄悄混用分词结果。超长单词（超过 128 字符单位）不入词表；查询超过 128 个不同词元时返回明确错误。

关键词查询使用 OR 召回、`ts_rank_cd` 排序，分数只表示此关键词算法的排序信号，不是答案置信度。词元由代码生成，SQL 使用参数绑定；用户不能注入 tsquery 运算符。空词元查询返回空结果。

游戏词典、口语别名、Embedding、pgvector 和 RRF 融合尚未接入；这个配置名不能冒充完整 RAG。

## 证据与补全

检索 SQL 同时限定 `build_id` 与 `release_id`。读取片段也检查所属索引；混入其他索引的 ID 会导致整次读取失败，不返回部分越界结果。

证据正文来自冻结的审核规则；引用位置来自 manifest 的原始来源，包含 blockId、documentId、PDF 页索引、印刷页码和 bbox。编辑解释以 `editorialExplanation` 单独返回。证据 ID 对应稳定片段 UUID，后续模型只能引用本次证据中出现的 ID。

关联读取将条件、例外、示例、补充关系视为同版本图，先保留首批命中规则，再按确定顺序补全关联。多层关联可继续扩展，重复和环路去重。受规则数量与证据 JSON 字符预算限制，放不下整条规则时返回 `PRIMARY_RULE_OMITTED` 或 `RELATED_RULE_OMITTED`，不会截掉后半段或假称证据完整。返回的关系只包含已纳入的两端，缺失规则列在 gaps。

`maxChars` 是证据 JSON 字符预算，不是模型 token 预算；后续 Agent 仍需对完整工具结果、关系、缺口及会话做总预算。相关规则不等于适用于当前局面，后续回答仍须检查适用条件。

## API 操作

统一前缀 `/api/admin`，Bearer 管理员认证，JSON 请求。响应包含 `data` 和 `requestId`；OpenAPI 包含完整 schema。

| 操作 | 路径 | 请求体 |
| --- | --- | --- |
| 冻结快照 | `POST /rulesets/{id}/releases` | `{ "name": "基础版审核知识 v1", "revisionIds": ["<approved-revision-id>"] }` |
| 快照信息 | `GET /releases/{id}` | 无 |
| 原文与规则清单 | `GET /releases/{id}/manifest` | 无 |
| 建立基线索引 | `POST /releases/{id}/indexes` | `{}` |
| 索引配置 | `GET /index-builds/{id}` | 无 |
| 关键词检索 | `POST /index-builds/{id}/search` | `{ "query": "工厂 蓝色花砖", "limit": 20 }` |
| 证据与关联 | `POST /index-builds/{id}/context` | `{ "chunkIds": ["<hit-chunk-id>"], "maxRules": 20, "maxChars": 32000 }` |

知识管理员可以查看这些实验产物。将来公众 Agent 必须由服务端绑定已发布的 ruleset/release/index，不能让模型选择这些管理端 ID。

## 验证与后续门禁

`npm test` 包括真实 PostgreSQL 上的并发幂等、防篡改、审批/版本范围、旧版本保留、跨索引拒绝、条件/例外补全、数量/字符预算缺口、超长规则事务回滚以及分词版本不兼容。迁移 rollback/reapply 由现有存储测试覆盖。

`npm run build && npm run test:http` 额外对生成的合成 PDF 走真实 Next.js HTTP：解析 → 测试审核 → 知识快照 → 索引 → 检索 → 原始来源定位。只有合成资料会被测试自动批准；用 `INGESTION_TEST_PDF` 指定的私有规则书仍停在待审核，不会自动形成可发布知识。

后续必须完成真实规则审核与标准题标注、向量/混合检索和对照评测、发布门禁、Pi Agent 的受限工具与引用验证，才构成可上线的问答后端。
